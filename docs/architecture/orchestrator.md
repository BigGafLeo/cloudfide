# Orchestrator

Rewizja 2026-10-14. Część [architektury](../architecture.md).

runAgent(context, bundle, config, adapters, signal) wykonuje: validate input/trust → analyst admission → analyst → plan validation → writer admission → writer → host materialization/freeze candidate. Zwraca CandidateManifest i patch. Brak krytycznego context, dispute albo invalid role output kończy fazę z reason, bez retry wewnątrz pary ról.

AnalysisBundle jest immutable wejściem: captured base/head diff, normalizowane wyniki narzędzi, inventory i potrzebne production source/existing tests. Selection zaczyna od changed unit, powiązanych istniejących testów i one-hop static imports widocznych w pliku; coverage-gap rotuje uncovered units z obu aktualnych raportów (najwyżej cztery na aplikację), ze stałymi priorytetami router, mutation/hooks/cache, formularze/błędy zapisu/usuwania/toggle i factory/lifecycle. Bez grafu zależności lub ogólnego rankera. Host wybiera materiały frontend/backend aktualnej roli. Bounded bundle ma 200 KiB. Critical file za duży lub niejednoznaczna zmiana bez potrzebnej dependency/contract daje missingCritical i inconclusive, nie niewidoczne obcięcie. Nie tworzymy RPC queries, pagination, fingerprint cache lub reuse.

Plan ma najwyżej 20 przypadków i 20 candidate files. Host sprawdza expected/requirementSource, confidence i allowlist; writer może tylko realizować ten plan albo zgłosić dispute. Merytorycznej poprawności oracle nie dowodzi walidacja schema. Reviewer oraz kontrolowane regresje zwiększają jakość dowodu, ale nie zastępują prawdziwego kontraktu.

Role metadata (ID/purpose/schema) i SKILL.md wczytuje trusted loader z control checkout. SKILL.md jest jedynym źródłem procedury roli; nie powstaje drugi prompt w roles/*.md. Procedures są oddzielne, reference wybierany według role/app/check. SKILL.md z PR nie jest odkrywany. skillsUsed opisuje faktycznie dołączone materiały; fixture test wykazuje, że backend-unit request nie ładuje frontend/mutation/other-role instructions.

Każdy dispatch dostaje nowy callId i świeże empty HOME/cwd, tylko credential wybranego providera i niezbędne runtime env. GitHub API recheck wykonuje host przed każdym call. Nie ma host retry, resume ani fallback. pr-change ma maksymalnie dwa core calls oraz jeden optional reviewer w jego jobie. coverage-gap uruchamia runCoverageRounds z najwyżej ośmioma parami analyst/writer i współdzielonym Budget (17 calls razem z opcjonalnym reviewerem). Budget i native output są częścią manifestu.

coverage-gap kumuluje tylko zweryfikowane treści testów w mapie i generuje patch względem niezmienionego captured original head. Każda partia przechodzi istniejący verifyCandidate z runAppProcess/Docker; nigdy bezpośrednie wykonanie aplikacji na hoście. Po sukcesie aktualizuje coverage, gaps i mierzone liczby testów. Historia ośmiu rund zawiera plany, checks, units, call IDs i wyniki; następny bundle dostaje jej krótkie podsumowanie oraz nowe testy. Identyczny patch nie jest ponownie weryfikowany. Nieudana partia pozostawia ostatni poprawny kandydat. Profil referencyjny ma noProgressRounds=3. Przed progiem liczy próby bez wzrostu coverage; po progu w trybie kontynuacji nowa zweryfikowana partia zeruje licznik także bez wzrostu procentów. Jej wartość semantyczną nadal ocenia final reviewer. Nieudane/no-change próby pozostają ograniczone. Stop następuje także dla limitu rund/budżetu/czasu, zbyt dużego kontekstu, cancellation i stale PR.

Próg raportowania to >=80% lines i >=80% branches osobno frontend/backend, liczony z covered/total przy total>0 oraz pomiaru pct. coverage.stopAtTarget jest opcjonalnym boolean z kompatybilnym default true; profil referencyjny ustawia false. Po progu selekcja może wracać do wcześniej analizowanych jednostek i zwalidowanych sourceLocation, oprócz bieżących luk. Są to wskazówki hosta; coverage.gaps pozostaje rzeczywistym pomiarem. Nie dodajemy ogólnego skanera wykluczonych plików. Trusted policy może podnieść target, nie zmienia configów aplikacji. Wymagana jest porównywalność, stałe mianowniki i brak regresji wszystkich czterech metryk. Oddzielny final verifier jest autorytatywny dla raportu reached/partial; accepted propozycji nie oznacza osiągnięcia celu. objectiveMet nadal oznacza oddzielną aspirację 100%.

Verifier i reviewer nie mutują planu/candidate. Publisher oblicza final decyzję na zwalidowanych wynikach, bez własnego modela. No-change/inconclusive/skipped może przejść bez candidate verifiera do publish. Missing artefact/job failure raportowany jest jako niekompletny run; nigdy synthetic passes.

## Wartość testu

Każdy przypadek planu wymaga value: action add/strengthen, testPath, existingTests z path/name, regression i rationale (wpływ błędu oraz koszt utrzymania/setup). Host przed writerem sprawdza rzeczywiste pliki w ograniczonym bundle, dozwolony cel i porównanie testu z tego samego pliku dla każdego istniejącego celu, także action add. Pełna mapa captured/current files służy wyłącznie hostowi do blokowania nadpisania pominiętego istniejącego pliku. Wybrane jednostki i ich bezpośrednie importy otrzymują powiązane testy, bez rekurencyjnego przejścia grafu. Po writerze wymaga pokrycia zaplanowanych celów. Nazwy testów i uzasadnienie są oceniane semantycznie; schema nie dowodzi braku duplikacji ani poprawności asercji.

Final reviewer dostaje oryginalny kod jednostek wskazanych w planie, powiązane testy i bezpośrednie importy, także gdy candidate tworzy zupełnie nowy plik. Brak wymaganego źródła lub porównywanego testu blokuje review. Profil demonstracyjny wymaga passed bez material findings; cały czas obowiązuje jeden dodatkowy call w ramach 17. Review nie dopisuje testów i nie ma automatycznej pętli napraw po review.

Review materializes the validated test-only patch in disposable scratch without executing application code. It follows direct imports in proposed tests while preserving original tests for comparison. References to tests created in earlier rounds are supplied by the exact candidate patch and labelled separately from original-snapshot evidence. Missing references from both snapshots and the proposal block review.

Końcowy reviewer ma oddzielny limit danych wejściowych 512 KiB, obejmujący dokładny cumulative patch, pełny plan, oryginalne testy i wybrane źródła. Limit bundle analityka pozostaje 200 KiB. Przy required review controller po mechanicznej weryfikacji partii, przed jej przyjęciem, buduje ten sam pakiet co final reviewer. Przekroczenie kończy rundy z context-limit, zachowuje ostatniego kandydata mieszczącego się w limicie i pełny rejestr wywołań. Nie usuwa dowodów ani nie obniża required gate.
