# Test value policy

Coverage locates unexecuted code; it does not establish whether assertions protect behavior. The 80% line/branch target is a reported milestone. The reference profile continues beyond it (coverage.stopAtTarget=false) for justified cases within the existing budget; stopAtTarget=true retains the cheaper threshold-stop policy. Neither setting requires inventing tests. The assignment does not set a coverage percentage. A valid proposal can remain partial when useful, supported work is exhausted.

The analyst compares tests in the supplied scope, then chooses strengthening or adding. Each case records a target, compared test names/paths, a concrete incorrect behavior, and impact versus maintenance/setup cost. Prefer strengthening an existing behavior test. Another input is justified when it distinguishes a different plausible regression; sharing a branch is insufficient evidence to delete it. Do not add a test solely to increase a percentage or a mutation score. Uncertain contracts belong in remaining gaps.

The writer implements approved cases and preserves prior protections. Assert the request/effect relevant to the claim, await meaningful async milestones and use real isolated state when testing cache behavior. Formatting-only SQL differences should not fail a semantic schema test. Mocked DDL does not establish behavior against a real database. Characterization must be labelled honestly.

The host validates bounded structured value evidence and in-scope references before writer spend, then checks planned targets against writer files. These are admission checks, not semantic proof. The fresh reviewer compares source, original tests, exact patch and verifier evidence. The demonstration profile requires review: unavailable or failed review, material findings, and any oracle-counterexample finding prevent accepted, including an oracle claim labelled minor. A surviving regression explicitly promised by a case, or rejection of contract-allowed behavior, must not be waived because another assertion is useful. Unclaimed optional gaps remain distinct. Unknown model claims make the result inconclusive; they never become confirmed facts by changing severity. It remains one final call in the existing budget, without an automatic repair loop. A reviewer can use a separately configured provider through the existing adapter interface.

The published report shows up to twenty escaped value rationales; the artifact retains complete plans. Impact and cost are qualitative judgments, not a numeric score. Acceptance does not establish a globally minimal test suite, complete oracle verification or a representative mutation score. Optional mutation checks remain separately configurable and disabled in the reference profile.

Review materializes the validated test-only patch in disposable scratch without executing application code. It follows direct imports in proposed tests while preserving original tests for comparison. References to tests created in earlier rounds are supplied by the exact candidate patch and labelled separately from original-snapshot evidence. Missing references from both snapshots and the proposal block review.

Analysis includes relevant tests for the selected units and their one-hop imported production units, using the same test matching rule. The host separately receives the complete captured/current file inventory: it refuses a plan that rewrites an existing output absent from the analyst context. Every case targeting an existing test file must identify a compared test from that file, even when adding a scenario. This does not parse test names or prove assertion preservation; required final review remains necessary.

Failed typechecks retain bounded compiler stdout/stderr diagnostics for the existing next-round feedback path; full raw logs remain separate. The reference profile permits three consecutive non-progress attempts, within the unchanged eight-round/seventeen-call limit. Before the target, progress means coverage growth. In continuation mode after the target, a distinct verified batch can strengthen assertions without coverage growth and counts as mechanical progress; the final reviewer still evaluates its value. Rejected, inconclusive and no-change attempts remain bounded. These changes address observed context loss and unhelpful feedback; they do not add an autonomous review-repair stage.

Continuation uses actual uncovered paths plus previously selected units and validated case locations as host selection hints. It does not fabricate reported coverage gaps, broaden discovery to excluded code, or prove global exhaustion from one bounded context. An already-covered callback or cancellation path can still merit an assertion. The role guides require observable callback/cancellation effects and stable semantic SQL obligations.

The rationale is assertion strength, not a higher universal percentage: [Stryker’s worked example](https://stryker-mutator.io/docs/General/example/) demonstrates that full code coverage can still leave incorrect behavior undetected. Our original-baseline diagnostics likewise found observable gaps after the 80% milestone.
